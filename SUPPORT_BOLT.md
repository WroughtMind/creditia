# Bolt.new: committed-file evidence from original HAR captures

Checked 2026-10-17. `crates/adapters/src/bolt.rs` now reads real line evidence from the current hosted client's original traffic contract. It does not use the old open-source ActionRunner's `complete` status or invent a typed successful `Write.result` schema.

## The verified save receipt and file body

The previously downloaded public shipping resources at `/private/tmp/creditia-cloud-client/bolt/` contain a stronger contract than the generic tool renderer:

- [prepare-body-qXgDsD6W.js](https://bolt.new/assets/prepare-body-qXgDsD6W.js), `isBoltMergedAnnotation` and `extractMergedShaFromAnnotations` (character offsets 1625 and 1751), explicitly recognize `{type:"bolt-merged", mergedSha:string}` in assistant message annotations.
- The same prepare-body bundle's `prepareRequestBody` (offset 6786) sends `projectId` and `codeStorageRepo:{sha:currentCommitSha}` in `POST /api/chat`. [serialize-messages-uu8F8s9A.js](https://bolt.new/assets/serialize-messages-uu8F8s9A.js), `serializeMessagesForRequest` (offset 1192), preserves message IDs, including the final user message. The current Chat client reads assistant `{type:"metadata",userMessageId}` annotations. Together these tie a saved result to that user turn's starting commit instead of treating any older preview synchronization base as the tool's original file.
- [Chat.client-DkyWj5Jm.js](https://bolt.new/assets/Chat.client-DkyWj5Jm.js), `applyBoltMergedImpl` (offset 1182929), obtains the current base commit, calls `applyChanges(projectId,{baseSha,sha:mergedSha})`, and applies the returned files and commit SHA. Its failure message explicitly distinguishes saved changes from a failed local preview update. Thus a saved merge does not require a successful browser preview.
- [workbench-CqEfvfNn.js](https://bolt.new/assets/workbench-CqEfvfNn.js), `applyChanges` (offset 451349), sends `POST /api/projects/{projectId}/apply-changes` and reads `{sha,files}` from the successful response. `applyCodeStorageCommit` (offset 474141) reads each file's `path`, `state`, optional `oldPath`; its file writer (offset 475503) consumes `{path,content,isBinary=false}`. `content` is the entire post-commit file, not a unified diff. Deleted and unmerged states do not supply successful new text; renamed files need a different baseline path and are conservatively skipped. A local apply failure throws; it does not silently manufacture success.
- The same bundle's `fileUrl` (offset 43548) constructs `/api/projects/{projectId}/files/{sha}/{encodedPath}?e`. [url-Cs89-ZjL.js](https://bolt.new/assets/url-Cs89-ZjL.js) first applies `routerEncode`: `~` becomes `~0`, `.` becomes `~1`. [path-BT1_87Vt.js](https://bolt.new/assets/path-BT1_87Vt.js) then URL-encodes each path segment. For example, `src/a.rs` becomes `src/a~1rs`. The storage reader consumes the response as bytes. The importer accepts textual UTF-8 bodies, including HAR base64 bodies, and reverses both path encodings.
- [api-client-DOdYlOlO.js](https://bolt.new/assets/api-client-DOdYlOlO.js) persists and reloads original `messages` and `parts` through `/api/chats/{projectId}`. The SDK reducer in [dist-CJFV4HHb.js](https://bolt.new/assets/dist-CJFV4HHb.js), `onToolResultPart` (offset 14617), joins `toolCallId` to the existing tool invocation and sets `state:"result"`. This state means a result arrived, not independently that the file was saved.

The current client's `fileWriteFromInvocation` recognizes actual proposal text in `args.content`, `args.file_text`, `args.new_string` and `args.edits[].new_string`. That function paints a design preview and does not prove success. Creditia instead requires the separate saved merge and committed bodies below. For `Edit`/`MultiEdit`, when the captured args also contain exact `old_string`/`new_string` replacement pairs, the importer uses them only as a strict before/after consistency check; it does not assert that every Bolt version uses those input fields or that matching inputs alone prove execution. Unrecognized tool/input variants are skipped.

A fresh direct read of the above official asset URLs returned HTTP 403 during this continuation. That restriction was not bypassed. These findings are from the already fetched public artifacts identified below, not a claim that the deployment can never change. No authenticated endpoint was called, no account was opened, no model was invoked, and no downloaded agent was executed.

## Accepted input and attribution rule

Place an original standard HAR (with response bodies) in `source_dir(Src::Bolt)`, normally `~/.bolt` or `CREDITIA_BOLT_DIR`. `.har`, `.json` and `.jsonl` files use the shared offline import plumbing. This implements a reader; it does not assert that Bolt offers a working one-click chat-history export or automatically obtain private history. No custom Creditia export envelope is required.

A line can be emitted only when all of these agree:

1. A captured successful `POST https://bolt.new/api/chat` request has `projectId`, `codeStorageRepo.sha`, and a final user message ID. The saved assistant's unique `metadata.userMessageId` must identify this same user turn; `codeStorageRepo.sha` must equal the apply request's `baseSha`. Conflicting starting commits suppress that turn.
2. A successful `GET https://bolt.new/api/chats/{projectId}` response contains an assistant tool invocation with a native `toolCallId`, its arguments, a returned result, and an unambiguous `bolt-merged.mergedSha` annotation. Both current `parts[].toolInvocation` and legacy `message.toolInvocations` are recognized and reconciled.
3. A successful `POST https://bolt.new/api/projects/{sameProjectId}/apply-changes` has a captured request `{baseSha,sha:mergedSha}` and response `{sha:mergedSha,files:[...]}`. A branch-only apply request, generic success object, failed HTTP request, mutable snapshot or tool preview is insufficient.
4. The same project, exact `baseSha` and API-relative path have an original textual body. It can come from a successful immutable `/files/{baseSha}/{encodedPath}` response or a previous `apply-changes` response whose returned SHA is exactly that base. Missing paths in a partial diff are never treated as empty files. A 404 is not an empty-file baseline.
5. The tool's explicit absolute path uses a root handled by the shipping client's `toProjectRelativePath`: `/home/project/`, `/tmp/cc-agent/{id}/project/`, or `/workspace/bolt-code/{id}/project/`. The resulting relative path must exactly equal the API file path. Traversal is rejected. The absolute path must separately match the normal `PathMap` project mapping, including a user-provided link when appropriate. The API's relative filename and a known repository filename never establish project membership by themselves.
6. `Write`'s complete proposed body must equal the complete committed body byte for byte. `Edit` and `MultiEdit` must replay from that exact base into the complete committed body. Missing/ambiguous replacements, binary/renamed/deleted/unmerged files, contradictory bodies and explicit tool errors are rejected. This excludes additional manual changes in the same commit rather than attributing them to the assistant.
7. Only `added_lines(before,after)` is emitted. Existing human context retained in a whole-file overwrite, unchanged lines and deletions do not become AI evidence. A submitted proposal with no saved change emits nothing.

The per-tool result remains opaque; neither absence of `type:"error"` nor `state:"result"` is treated as the saving receipt. The captured turn-start commit, independent merge, immutable base, whole committed body, and exact proposal replay establish the evidence together. Known `type:"error"`, `isError`, `is_error`, explicit false success/ok and failed/cancelled statuses veto a conflicting observation.

## Identity, metadata and integration

`scan(store,pm,stats)` rebuilds the available Bolt native import set into its own `bolt:native-import:` group. Native calls reconcile by `(projectId,toolCallId)` across HARs and repeated current/legacy parts. A failed or altered copy suppresses that call; conflicting immutable `(projectId,sha,path)` bodies suppress that file. The same committed `(projectId,sha,path)` is emitted once even if more than one call represents it. Distinct commits containing identical new text retain distinct occurrences. Project-scoped write observations mark their rebuilt sessions for atomic library synchronization, even when a conflict leaves no successful evidence. This removes rejected rows and old model/occurrence variants from SQLite before analysis can restore them. Completely missing imports assert no retraction; the existing historical-library fallback still applies. As for other live sessions, the currently available import set takes precedence over older stored pages.

Sessions use the actual cloud project ID. Unique captured user-message IDs provide the prompt count only for sessions that yielded mapped evidence. No HAR capture timestamp, message creation time, project edit time or file fetch time is used as a tool execution timestamp. Per-write model is empty/unknown and time is `0`/unknown; the mutable top-level selected model is never backfilled. `discover()` returns no guessed cwd. `doctor()` reports the exact narrow HAR contract and missing-baseline limitation. The root caller integrates `scan`, replaces the old Bolt doctor gap row, and retains the other cloud metadata readers.

Remaining boundaries are explicit: no real-account acceptance capture was available or attempted; new files without a verified empty baseline are skipped; an assistant message with several separate edits to one file is skipped unless an individual captured invocation independently reproduces the complete committed after-body; several edits inside one `MultiEdit` are supported. Arbitrary shell rewrites, notebook edits, branch-only persistence, missing response bodies and unsupported result/input variants do not become line evidence. These limits are not a claim that Bolt cannot preserve the underlying data.
